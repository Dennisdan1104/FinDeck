# Agent Note: 圆桌发言者听得到全场，且全场进入日志

Status: implemented

[English](2026-09-11-roundtable-grounding-and-logged-room.md) | 中文

## 问题

圆桌的开桌配置带着三处让功能不可用的缺陷上线，另有两条架构缺口：

- 深究档的发言者根本收不到全场。引擎只在浅谈分支里拼出转录与轮次指令，而深究分支交给研究窗口的是一个空消息列表，于是首次深究请求只有发言者契约加一份工具目录，既没有用户的问题，也没有此前的发言。发言者在盲区里检索、再给出没有依据的发言——这与包 README 自己对请求的描述相矛盾。
- 开桌配置再也回不去。开桌会设置桌面，而没有任何路径把它清掉；页面只在没有开桌时渲染设置面板——于是深浅、人员模式与模型在宿主进程的整个生命周期里被冻结。已交付的文案却承诺"清空圆桌"后设置会回来。
- 用户自建的名单永远只能有一个人。标着"加一位"的控件实际新建了一份名单，而没有任何控件往正在编辑的名单里加人。也没有任何地方能标记由谁收尾，尽管名单模型与状态机都支持主持人。
- 该包不写任何会话事件，因此凡是进入发言者请求的内容都无法从日志重建，违反仓库"模型可见的输入必须伴随会话事件"的规则。
- 研究工具的执行没有 agent，因此相对路径按部署的工作目录而非用户工作区解析，会话级守卫与用户审批策略也看不到这些调用。

## 决策

- 引擎只构建一次全场上下文，并把同一条开场消息同时交给浅谈请求与深究研究窗口，因此每一次发言者请求——包括被强制的最终作答——都从转录与轮次指令出发。
- 清空圆桌即释放开桌配置。设置面板按记忆的选择预选返回，两种语言的文案都照此说明。没有新增动作或 Remote 方法，因为 UI 早已做出的承诺就是这个行为。
- 名单编辑器新增真正的"往本名单加一位"控件、一个单独命名的新建名单控件，以及一个单选的主持人（收尾人）组。新席位从该部署列出的第一个内置身份播种，因此用户还没输入任何内容时它就能发言。
- 三个会话事件经 `SessionEventMap` 声明合并定义，并在各自的提交点追加：开桌及其就座发言契约、每一条并入全场的条目、以及每一个完成的轮次——携带该请求实际使用的全场文本、发言、引用、是否因限额结束，以及深究轮次的工具往来。
- 记忆的人员模式若已不存在，会在配置解析时回落到默认值，并记录一条说明失去了什么的全场条目，因此一个过期的设置值无法再拒绝用户的消息。
- 记忆开桌配置在设置提供方只读时跳过写入，写入失败则就地捕获并记录警告；开桌本身从不依赖它。
- 研究窗口把调用方的中止信号与截止时间一并传给工具执行。
- 未知的深浅档与未知的模式类型被点名拒绝，而不是被静默强制转换。

## 备选方案

**给深究发言者一份自己的研究提示，让它自行推导问题。** 否决：全场文本正是让一次发言可被回答的东西，自行推导会让两位发言者对"被问的是什么"产生分歧。

**新增一个显式的"另开一桌"动作，而不是清空即释放。** 暂缓：清空本就意味着"这次讨论结束了"，且 UI 文案已经承诺设置会回来。用第二种方式到达同一状态，需要它自己的确认文案与 Remote 表面。

**把这些圆桌事件标为 ignorable，好让旧构建能读含它们的日志。** 否决：这些事件携带模型可见的输入，`ignorable` 会让某个构建跳过后续模型请求所依赖的输入。正确做法是重新生成事件目录。

## 影响

- 深究发言回答的是被问的那个问题；即使检索一无所获，发言者也仍从全场作答。
- 首桌之后开桌配置可以再次进入，且设置面板显示的就是实际会被使用的人员模式。
- 自建名单可以容纳多位成员、可重排、并可指定一位收尾人。
- 由 agent 驱动的圆桌运行可以从会话日志重建。已交付的浏览器路径在协议上仍没有 agent 身份，因此在该路径上全场不入日志、研究工具也没有会话作用域；两者都记在包 README 的限制里，而要真正落实需要在 Remote 调用中建立 agent 身份。
- 重新生成持久化目录是本改动的一部分：这些事件是按需必读的，因此未重新生成该目录的构建会拒绝含有它们的日志。
