# Agent Note: 模式创作只在可写根内产生可读的 preset

Status: implemented

[English](2026-09-11-preset-authoring-write-integrity.md) | 中文

## 问题

模式创作工具（`mode_list`、`mode_write`）让创造模式会话新建与改写 preset。对该改动的评审发现，写入路径有四种方式会产出自己的读取方无法使用的状态，另有一处部署缺口：

- `renderPresetDocument` 把步骤的 `model` 作为裸标量插进 YAML，而 `flowProblem` 接受任何含斜杠的字符串。因此带换行的模型路由会在第 0 列注入一行：新键静默落地，重复键让文件无法解析，两个读取方都退化成 `{}`——模式就此消失，而 `mode_write` 仍报告成功。
- 改写路径从持有该 preset 的任一个用户根解析，却写进第一个用户根。存在两个 `user` 信任根时，这会创建一个没有组合的目录，discovery 把它报告为损坏，并且由于根是先到先得，它会遮蔽真正的 preset。`deleteComposition` 早就带了写入路径缺失的那个归属守卫。
- 新建先整目录复制、再写文档。第二步写失败时，复制出来的目录留在名册上，带着来源的描述且没有声明，而调用方被告知写入失败。
- `name` 为空时不会渲染任何元数据，于是写入被跳过，而 `save` 返回成功。
- `resolveAuthoredFlow` 把既不是 `free` 也不是缺省的任何 `modeKind` 当成 `work`，因此线上调用方可以传 `"banana"` 并得到一个工作模式。
- `cordis` preset 新增的行挂载 `@deepseek-ai/dsh-tool-preset-authoring`，而运行时依赖清单没有声明它。discovery 从 harness base 向上查找来解析行包，因此安装后的部署会把创造模式报成损坏——而这正是该功能存在的理由。

## 决策

写入路径只产出读取方能加载的 preset，并且只写到已解析出的 preset 所在之处。

- 渲染器把每个非标识符标量都经 `JSON.stringify` 输出，`flowProblem` 拒绝步骤模型里的控制字符。加引号是写入方的性质，因此任何值都无法变成文档结构；校验则让无意义的值在写入与 discovery 两处都响亮失败，因为同一段文本还会按每步一行进入面向模型的流程段。
- `writePresetDocument` 与 `deleteComposition` 共用同一个 `ownedPresetDir` 守卫，因此改写一个可写根并不拥有的 preset 会被拒绝，而不是写进错误的根。
- 文档写入失败会回滚已复制的目录，因此失败的新建不会在名册上留下条目。
- 空白的显式 name 读作缺省，依次退回已存名字、再退回 id，与读取路径本就把空串当作"无显示名"的语义一致。
- 未知的 `modeKind` 被点名拒绝，而不是被强制转换。
- 运行时依赖清单声明该工具包及其必需的同级依赖。

## 备选方案

**只转义会破坏裸标量的那些字符。** 否决：这会让保证依赖于手写的 YAML 规则，而后续任何一次校验放宽都可能扩大它。用一个已有的序列化器给单个标量加引号不需要这类推理，并且与相邻的自由文本字段的既有输出方式一致。

**把空 name 拒绝掉，而不是规范化。** 否决：读取路径本就把空串当作"无显示名"，选择器也已经退回 id；拒绝会使得 `save({id, name: ''})` 失败而 `save({id})` 成功，尽管两者表达的是同一件事。

**允许改写写进靠后的用户根。** 目前否决：那样保存与删除就会对"哪个根拥有该 preset"产生分歧。若某部署需要第二个用户根里的 preset 可编辑，该守卫是唯一要改的地方——且删除必须同步改。

## 影响

- 工具写出的 preset 就是 discovery 能加载的 preset；被拒绝的写入不改变名册，并点名其规则。
- 拥有多个 `user` 信任根的部署无法改写位于靠后根里的 preset；它会被告知不可写，而不是被静默写到别处。
- 安装环境能解析到创作工具，因此创造模式会被激活，而不是报告一个损坏的行。
- 新建路径多读一次名册，因为写入目标刻意取 discovery 解析出的那一个。
- 带换行的步骤 `label` 仍会原样进入面向模型的流程段。它无法改动文档，且创作本身已是 shell 级信任，故维持现状。
