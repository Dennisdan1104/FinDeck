# Agent Note：模式创作——步骤的用途，与只写元数据的写入路径

Status: implemented

[English](2026-09-09-mode-authoring-and-step-purpose.md) | 中文

> AlphaDeck 工单 A（需求 R9 配置自由度）。记录工作模式的一步为何只增加一个可选「用途」字段、而不是一张更大的必填表，以及两个创作调用方——模型与资产页——为何都只写预设的元数据那一半。

## 问题

`FlowStep` 只有 `id`、`label`、`model` 三个字段。没有任何地方写明一步是为了什么，于是每个工作流的实际内容都堆在一份所有模式共用的通用技能文档里。复制某个工作预设而建出的模式因此只是空壳：它重排了步骤条，却没有改变任何模型被告知要做的事。唯一的创作入口是资产页的表单，它要求复制一个既有工作预设，且只收 `from`/`id`/`name`/`steps`；而运行在能自我修改的 `cordis` 预设上的会话——本来就能写任何文件——反而没有任何带校验的方式建模式：它手写 YAML，于是一个非 kebab-case 的 id、或把裸提供方名当作 `model`，会产出 discovery 判为 broken 的预设，而写入当时没有任何反馈。

## 决策

**流程步骤增加一个可选的 `prompt`：这一步做什么，写进模型自己的指令里。** 它渲染在 `mode:flow` 提示词分段中该步骤条目之下，并与条目对齐缩进，于是多行散文仍留在列表项内。这个字段是「最强意义上」的可选——键缺失读作「这一步只以标签命名」，与字段出现之前声明的每个流程读法完全一致——而键存在但留空会被拒绝而非存下，因为 `prompt: ""` 是一条什么也不表示的声明。这正是「字段尽量可选、表达仍然自由」的平衡：schema 保持三个必填字段加一个长文本位，建模式永远不是填表，也永远不是空壳。

**用途是指令文本，不是步骤数据。** 它补充 agent 的既有指令而非替换它们；它不进入 `flow_step` 的结果（一次声明仍只回答步骤的 id、标签与模型）；它不 gate 任何东西。另一个备选——枚举式的每步策略（`tools`、`checklist`）——被否决：某一步写着「这步只准搜索」会让模型追问为什么，而运行时没有任何东西能回答。

**两个调用方共用一条创作缝。** `AgentPresets.save`（`savePreset` Remote）接收 `AgentPresetWriteRequest`——`id`、可选的 `from`，以及可创作的那一半：显示名、描述、`modeKind` 与步骤——它取代了只能新建、参数形状相同但按位置传参的 `createFlowPreset`。给了 `from` 即新建：整目录复制来源，随后只写它的 `preset.yml`。不给 `from` 即改写某个既有用户预设：省略的字段保留已存值（只改步骤时连已存的 `modeKind` 也保留），组合从不被触碰。组合不是任何一条路径的参数，因此调用方写出的模式不可能给会话带来源预设本来没有的能力。

**模型通过工具而非文件系统抵达这条缝。** `dsh-tool-preset-authoring` 提供 `mode_list`（名单及每个模式声明的步骤，`trust` 标出可写入的对象）与 `mode_write`（新建或改写，并在工具描述里明确把组合排除在外）。它由随包发布的 `cordis` 预设挂载，因此创作是「本就拥有 shell 访问权的那个模式」的一项能力。工具自身的翻译保留了线上类型要求显式化的那些缺省：省略的 `name` 保持省略，好让改写沿用已存名；步骤省略的 `model` 变成 `default`。

**渲染器是共享的，所以两处声明不可能互相矛盾。** `renderPresetDocument` 由它拿到的步骤表推导模式——有步骤即 `work`，空列表即 `free`，`undefined` 则不存模式——并通过复制路径同样使用的 `renderPresetMetadata` 渲染展示那一半。它取代了 `save` 里手写的行拼接：后者在自由模式分支里根本不写 `mode_kind` 行，于是一次改写为 `free` 会把已存模式留成「未声明」。

## 考虑过的备选

**把每步描述设为必填** —— 否决。现存每个模式都会因此失效，或被迫获得一段没人写过的描述，而需求明确要求建模式不能变成填表。

**把步骤用途作为技能之后的第二个提示词分段追加** —— 否决。流程、当前步骤、以及每步做什么是一份声明；拆到不同分段会让读提示词的人看到步骤列表却看不到说明这些步骤为了什么的那句话。`mode:flow` 本就位于第一方序号 100，而 skill 的文本稍后作为工具结果进入对话，所以在同一分段内追加才能让用途贴住它那一步。

**每步工具范围** —— 随需求一并否决。工具是会话级的，按步骤收窄多半只会让模型追问为什么这步不能搜。

**让 `mode_write` 编辑 `agent.cordis.yml`** —— 否决。组合正是让预设成为一项能力授予的东西；一个能改写它的工具会是一个更不可审计的 `bash`。想换插件集，受支持的做法是从 `from` 新建，这也正是网页表单一直以来的边界。

## 后果

两个调用方现在共用同一条带校验的写入，因此 discovery 会拒绝的 id、模型路由或流程形状，会在调用处以点名规则的方式被拒绝；资产页则在每一步旁边渲染它的用途。改写替换整份步骤表，没有「改一步」的操作，这也是 `mode_list` 完整返回步骤的原因。会话运行期间写入的模式，对之后新建的会话可见、对正在运行的会话不可见：已组合的会话保持启动时的插件组合，只有步骤声明会被重读，因此改写后的流程会在该会话下一次声明步骤时生效。`cordis` 的人设现在把元数据那一半指向工具，并把直接改文件留给组合——那正是这些工具刻意不拥有的另一半。

## 验证

`packages/preset/agent-presets/tests/mode.spec.ts` 覆盖步骤形状：声明的用途随步骤读回，省略的用途不产生键，留空的用途被拒绝。`packages/preset/agent-presets/tests/remote.spec.ts` 在临时根目录上驱动创作缝：从来源新建会带上来源的描述并丢掉它的 `order`，改写保留已存描述与名称，`free` 丢弃流程并落盘为 `mode_kind: free`，而各类拒绝（空 id、无步骤的 work 声明、非法步骤、已占用 id、未知来源、随部署发布的预设）都点名各自的规则。`packages/preset/tool-preset-authoring/tests/tool-preset-authoring.spec.ts` 对真实名单执行两个工具并断言落盘文件，包括复制来的组合与来源逐字节相同。`packages/preset/mode/tests/mode.spec.ts` 断言渲染出的流程分段带上缩进的用途，而一次 `flow_step` 声明仍只回答 id、标签与模型。`packages/client/ui-assets/tests/assets.client.spec.tsx` 在展开的流程卡里渲染用途，并断言表单把它转发出去。
